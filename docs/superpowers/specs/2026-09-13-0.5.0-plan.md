## 1. ValueConverter SPI（自定义类型处理器）

**动机**：JPA `@Convert` 只覆盖"字段级、启动期确定的转换"；缺"全局按 Java 类型注册"
的轻量入口（对标 MP `TypeHandler` / jOOQ 强制 Converter）。典型场景：项目统一的
Money/手机号/加密字符串类型。

### API 草案

```java
public interface ValueConverter<A, D> {
    D toDatabase(A attribute);
    A fromDatabase(D dbValue);
    default Class<A> attributeType() { return null; }   // 全局注册时用于类型匹配
    default Class<D> databaseType() { return null; }
}

// 全局注册（启动期，LightQuery 静态门面）
LightQuery.registerConverter(Money.class, new MoneyConverter());

// 字段级仍用 JPA @Convert（优先级：字段级 @Convert > 全局注册 > 默认 JDBC 映射）
LightQuery.clearConverters();   // 测试用
```

### 契约

- 匹配规则：字段属性类型 `assignableFrom` 注册类型即命中；同一类型重复注册后者覆盖
  前者并告警（dev 日志/异常，决策点见 §5a）。
- 生效点：`ColumnMeta.toDbValue / fromDbValue` —— 即 insert/update/upsert、
  where 绑定值、结果映射全链路生效（与 @Convert 相同路径，T22 同款）。
- 主键/版本列同样生效；`null` 一律直通（转换器不拦截 null）。
- 转换器抛异常 → 包装 MappingException（消息含字段与类型，指出修复方式）。

### 测试（T29 ConverterRegistryH2Test）

全局转换器往返（insert/select/条件绑定/聚合投影）、字段级 @Convert 优先级、
null 直通、重复注册行为、转换器异常包装、子类型匹配（register(Number.class)）。

### 风险

子类型匹配可能误伤（register(Number.class) 影响 Long 列）→ 契约写死"精确类型优先，
assignable 次之，多命中取最近祖先"，不确定时宁抛勿猜。

## 2. 条件组合 API（Condition 树一等公民）

**动机**：`Consumer<Where>` 已可复用（T23）但不可组合/取反/传参复用；
jOOQ `Condition.and/or/not` 是该领域的正确抽象。0.4.0 强类型改造后
`TypedColumn` 持有完整类型信息，具备落地条件。

### API 草案

```java
// TypedColumn 条件构造产物不再只有"挂到当前查询"一种去向：
Condition active  = col(User::getStatus).eq(ACTIVE).toCondition();
Condition grownUp = col(User::getAge).ge(18).toCondition();

Condition spec = active.and(grownUp.or(col(User::getName).like("a%").toCondition()));

// 挂到任意查询（可复用、可组合）
LightQuery.queryable(User.class).where(spec).toList();
LightQuery.queryable(User.class).where(spec.not()).toList();

// Updatable/Deletable/JoinOn 同款接受 where(spec)
```

### 契约

- `Condition` = 现有 `ConditionGroup/Condition` 树的只读视图（不可变），
  挂入查询时深拷贝进模型，同一 spec 挂多个查询互不影响（对比现在
  `Consumer<Where>` 复用是安全的，spec 复用同样安全）。
- `toCondition()` 只能在列柄条件终端调用（eq/gt/like/…）；`isNull` 等无参条件同款支持。
- 逻辑删除过滤、逻辑组合语义（and/or 分组）不变——spec 整体作为最外层 AND 组的一个子树。
- 既有 `Consumer<Where>` 入口保留（不破坏），文档标注 spec 为推荐形态。

### 测试（T30 ConditionCompositionH2Test + SqlSnapshotTest 双方言快照）

and/or/not 嵌套渲染快照、同一 spec 挂两个查询、spec 与 inline 条件混用、
join 场景列别名解析、Updatable/Deletable 挂 spec、逻辑删除组合不变性。

### 风险与工作量

**0.5.0 最大工程**。风险点：TypedColumn 现在直接往 model 写条件，
需要拆"收集"与"挂载"两条路径；快照可能大面积更新（SQL 字符串不变则快照不动，
以"SQL 字符串零变化"为放行线）。回滚线：若拆路径伤及核心渲染，
缩水为 `where(Consumer<Where>...)` 可变参数组合（仍可组合但无 not()），保 0.5.0 时间点。

## 3. 审计 SPI（决策点最大，建议缩水）

**动机**：FillListener 只能"填字段"，拿不到操作类型/参数上下文/跳过能力；
对标 MP `MetaObjectHandler` + JPA `@PrePersist` 的诉求是"写入拦截"。

### 推荐方案（缩水版）：FillListener 增强，不新增 SPI

- `FillListener` 接口加 default 方法 `default boolean enabled(Operation op, Object entity) { return true; }`
  （返回 false 跳过该次写入？——**否**，跳过写入语义太危险，不采用）。
- 实际增量只有"操作类型"一个参数：新增
  `default void onWrite(Operation op, Object entity) {}`（op ∈ INSERT/UPDATE/UPSERT），
  onInsert/onUpdate 保留继续回调（向后兼容）。
- after 钩子不做：框架不持有行级 after 语义（批量场景行数不明确），避免伪契约。

### 否决方案（留档）

独立 `AuditListener(before/after/Operation/快照)`：需要行级快照与 after 钩子，
JDBC 层拿不到稳定 after 语义（批量、生成键），伪契约不如不做。

### 测试（T31 并入 FillListenerH2Test）

onWrite 三种操作类型触发、默认实现零影响、异常传播不变。

## 5. 需要拍板的决策点

a. **ValueConverter 重复注册**：抛异常（严格，推荐）还是后者静默覆盖（宽松）？
b. **ValueConverter 全局匹配粒度**：只精确匹配（安全，推荐）还是含 assignable 子类匹配（灵活但可能误伤）？
c. **条件组合**：接受 §2 的 `toCondition()` 方向，还是 0.5.0 先做回滚线的轻量版（`where(Consumer...)` 可变参数）？
d. **审计 SPI**：接受缩水为 `FillListener.onWrite(Operation, entity)`，还是整个移出 0.5.0？
